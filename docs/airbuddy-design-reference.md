## 1. 两种定位：借鉴体验，而不复制架构

| 维度 | AirBuddy 参考实现（以所查源码为准） | TXBoard-Gateway 的长期目标 | 采用决策 |
| --- | --- | --- | --- |
| 产品定位 | 针对 V2Board/XBoard/Xiaoboard 的中间件：加密转发、免登录目录/下单、验证码、SMTP | 为 TXBoard 的 Vue/React/Next.js/SPA 主题提供 **版本化 API Contract + 统一 SDK + 可选安全能力** | 保留 Gateway 的契约优先路线 |
| API 路由 | `/api/v1/:segments*` 通用代理，另有 `/api/v1/r8d/*` 扩展路由 | 固定 `/gateway/v1/*`，按 operation 白名单与明确的权限声明 | **不**照搬通用路径代理 |
| 应用层加密 | AES-128-GCM，浏览器与中间件配置相同的共享密码；路径哈希混淆 | HTTPS 必选；可选基于标准公钥封装的已评审协议，含抗重放和轮换 | 借鉴 SDK 无感调用体验，不照搬共享密码和路径隐藏 |
| 免登录购买 | 用用户/管理员能力创建账户和订单，再将身份返回给客户端 | **快速购买流程**由 Laravel 按业务权限、邮件校验/风控和持久化幂等实现 | 借鉴一体化 UI，重构执行方式 |
| 人机验证 | 图片数字验证码、哈希和时间戳校验 | 优先复用 TXBoard 现有 Turnstile / reCAPTCHA 服务端校验，加一次性挑战、限流与审计 | 不照搬可重放的 stateless hash |
| 通知/邮件 | 独立 SMTP 与自定义邮件模板，免登流程中发送账户信息邮件 | 复用 TXBoard 现有邮件通道与模板扩展，不重复建 SMTP，不发明文密码 | 只借鉴可配置的通知体验 |
| 部署 | Docker / Node.js / 编译产物等多方式 | Node/Hono 独立、私有网络、仅反代特定前缀、可选启用与回退 | 借鉴轻量独立部署，不急于换运行时 |
| 权限与日志 | 源码包含启动取得管理员令牌、打印请求体/令牌等代码 | Gateway 不持有管理员账号/令牌、不记录敏感请求/响应、不代用户操作资金 | **明确禁止照搬** |

**重点：**“将请求加密”不是“防墙、不被识别、不能抓包”的可证明承诺；HTTPS 与应用层加密也不能替代 Laravel 鉴权、验证码、速率限制或交易幂等。

## 2. 借鉴点 A：加密代理的“主题无感体验” → SDK 安全传输适配器

**要保留的体验：**前端主题只需要调用 SDK，例如 `txboard.orders.list()`，不必自己处理请求封装、错误响应或密钥协商；开启加密后无需逐主题改造业务页面。

**不能照搬的实现：**

- 不通过浏览器内置、公开配置或全站共享的固定对称密码“保密”。
- 不依赖 SHA-1 路径哈希、接口改名、代码混淆阻止恶意调用；合法用户仍可自行发请求。
- 不让客户端决定是否可以对**服务器强制加密**的接口降级到明文。
- 不声称应用层密文可以隐藏 IP、DNS、TLS 握手元数据或消除流量封锁。

**TXBoard 拟议技术设计（M4，需安全 ADR 批准）：**

1. 定义 `encryption=disabled | optional | required` 的 **服务器端 operation 策略**；默认仍是经过验证的 HTTPS。
2. Gateway 提供带协议版本、算法标识和 `kid` 的公钥发现；服务端私钥只保留在受控存储中。
3. 在安全审查后评估成熟 HPKE + AEAD 库，实现 SDK 自动封装与网关解封；按 `method + operation + gateway major + requestId + authenticated principal` 绑定验证上下文（例如 AAD）。
4. Redis 原子一次性 anti-replay 票据 + 明确时效；Redis 故障时敏感写操作 fail-closed，**不**以 Redis 代替 Laravel 的持久交易去重。
5. 提供双密钥窗口轮换、吊销、错误恢复、浏览器/Node 互操作向量和 p95 开销量测。
6. 对加密要求的服务器政策，SDK 与 Gateway 必须共同拒绝意外明文降级；无安全评审则该功能保持不启用。

**验收信号：**Tamper/重放/换路径/换用户/过期 `kid` 被拒绝；旧主题在非强制加密路由继续正常运行；端到端 E2E 的响应与未加密路径业务语义相同。映射 **GW-401～406**。

## 3. 借鉴点 B：免登录查看套餐 / 支付方式 → 明确的公开目录 API

AirBuddy 的“无需先创建用户就看商品和可用付款方”很实用，但公开支付方式是否可展示，必须取决于 TXBoard 后端的站点配置与字段脱敏规则。

**TXBoard 拟议行为：**

- **已具备**：`GET /gateway/v1/plans` 读取 TXBoard 公开套餐；`bootstrap` 提供站点与主题公开配置。
- **待设计**：`GET /gateway/v1/catalog/payment-methods`（示例路径，**未实现**）。必须先确认 Laravel 可安全提供哪些支付方式的**公开展示字段**，例如标识、名称、图标、币种与是否可用。
- 私密 API 密钥、支付商配置、账户结算信息不得出现在公共响应。不得让 Gateway 为了获取这些信息持有管理员凭据。
- 公开列表只用于浏览 UI；用户提交交易时仍由 Laravel 重新检查套餐有效期/库存或售卖状态、支付通道可用性、价格、优惠券以及用户限制，客户端报价永不可信。
- 若后端尚无合适公开数据合同，**先在 TXBoard 增加只读、最小字段的 public DTO**，不通过绕过鉴权的代理拼凑。
- 对公开接口做缓存时限定 TTL 和失效机制；避免个人化响应进入 CDN/共享缓存。

**验收信号：**访客可查看安全目录；配置隐藏的支付渠道不会泄露；交易层实际返回金额与订单合同一致；关闭功能开关后旧页面不受影响。映射 **GW-301 + 新增 GW-311**。

## 4. 借鉴点 C：免登录下单 → 安全“快速购买 / 注册与购买一体化”

**借鉴用户体验，不借鉴管理员代创建用户或关闭邮箱验证。**

推荐流程（拟议，需独立跨仓 ADR）：

```text
访客选套餐 → 服务端获取公开报价 → 填邮箱 / 验证码 / 邀请信息
     → Laravel 检查站点注册规则、邮件验证和防刷
     → 建立仅该用户可访问的注册或临时购买上下文
     → 受控完成用户注册与认证 → 服务端生成幂等订单
     → 支付沙箱/正式支付服务 → Laravel 验签与订单交付
```

**不变量：**

1. 不能为了“快速购买”自动关闭 TXBoard 邮箱验证、邀请码限制、账号存在性处理或风控；如要求邮箱验证，就必须走完服务端验证。不能调用管理员创建用户接口代替普通购买授权。
2. 不发送明文密码邮件；不在 Gateway 保存或输出密码、密钥、邮件验证码、Bearer、完整订单请求。
3. 老用户用受控登录/认领流程继续购买；禁止“填写邮箱即可取得现有用户身份”，也不能泄漏用户是否存在。
4. 认证与付款区分：注册成功不等于已支付；订单创建不等于已支付；支付回调由 TXBoard 现有独立路由完成且必须验签。
5. `Idempotency-Key` 由 Laravel 绑定真实用户和操作并持久化（唯一约束 + 事务 + 冲突语义）；同键重试返回同一订单，不同键由业务状态机控制，网关和 Redis 只是附加防刷。
6. 对用户关闭窗口、订单创建后断网、重复点击、支付成功但前端超时、重复支付回调等分别定义恢复页和可查询状态；用户界面显示真实状态而不是总提示“下单成功”。
7. 全流程以 opt-in 功能标志启用；新旧客户端一致遵循后台配置，不让旧 `/api/v1` 路由成为业务绕过入口。

**验收信号：**用户可在受控的一体化流程完成注册/购买；邮件校验或邀请码打开时仍正确执行；100 个并发重试不重复建单/扣费；老账号不会被他人用同邮箱接管；沙箱支付及重复通知全绿。映射 **GW-302～309 + 新增 GW-310**。

## 5. 借鉴点 D：图形验证码 → 可插拔挑战 / 分布式抗滥用

AirBuddy 有针对登录、注册、快速订单的验证码开关。TXBoard 需要的不是“再增加一套彼此冲突的验证码”，而是统一的风控抽象：

- 首选 TXBoard 已支持的 Cloudflare Turnstile / reCAPTCHA，由 **Laravel 服务端**根据站点策略判定，通过后按操作绑定结果。
- 如未来确需自托管图片挑战，需独立插件化实现，并使用密码学安全随机数与不可预测 ID、短 TTL、尝试次数限制、**Redis 原子一次性消费**；跨 Gateway 多实例不得重复使用挑战。
- 登录/注册/下单分别设置风险等级，验证服务于每种 operation；图形验证码只是附加门槛，不得代替账号、IP、会话限流。
- 不因为 `Origin` 缺失、验证码 UI 隐藏或客户端声明“已验证”就跳过服务端策略；失败要有明确错误码和可访问的替代流程。
- 对验证码过期、重用、错答、并发、Redis 宕机、恶意高频请求写测试，审计中不存储验证码答案/令牌。

**验收信号：**一次挑战至多成功消费一次；全分布式场景同一票据并发只能通过一次；错误码和节流一致；无侵入更改现有 TXBoard 验证开关。映射 **GW-203/202/206 + 新增 GW-209**。

## 6. 借鉴点 E：SMTP / 可定制邮件模板 → 复用 TXBoard 通知体系

AirBuddy 独立发送注册通知，包含可定制模板。TXBoard-Gateway **不另建独立 SMTP 服务**，避免双份邮箱密码与配置漂移。

- 在 TXBoard 内的通知/邮件服务统一处理注册、订单创建、支付成功/失败、到期提醒；Gateway 不持有 SMTP 账号。
- 由 TXBoard 后台配置可审查的模板及可替换占位变量，模板渲染必须进行 HTML 转义和白名单字段限制；不要把任意远程 HTML URL 当作可信动态模板执行。
- 严禁邮件发送登录明文密码、可直接使用的长效 token 或完整用户密钥；需要首次设置密码时使用短期一次性安全链接。
- 使用异步队列、失败重试/退避、去重和投递监控；与真实订单状态机绑定，避免同一支付回调重复发送邮件。
- 单独验证 SMTP 配置、域名 SPF/DKIM/DMARC 与模板转义；网关只传必要事件标识，不承担敏感业务邮件正文生成。

**验收信号：**同一业务事件最多按业务策略发送一次；邮件模板测试可控、无 XSS/凭据泄漏；SMTP 故障不回滚已完成的合法交易。映射 **新增 GW-312**。

## 7. 借鉴点 F：轻量、独立部署 → 可选服务与无痛回退

AirBuddy 提供 Docker 和直接可执行方式，说明“独立安装、小体积、低运维成本”值得作为用户体验要求。

- 保持 Node.js + Hono 的现有技术栈，先量化内存占用、冷启动、p95 新增延迟、镜像大小和依赖漏洞，再考虑额外运行时或二进制发布方式；**不因对方使用 Bun 就直接迁移**。
- 首选 Docker 非特权、只读文件系统、私有网络，入口反代 **仅** `/gateway/v1/*`；管理端、订阅、TX-Node、支付回调、插件和 WebSocket 不经此路由。
- 提供 Docker/Compose 示例、部署清单、配置检查、网关健康/readiness、升级/回滚脚本；不要求安装方掌握额外管理员凭据。
- 渐进推广：兼容版本探测 → 内测主题 → 灰度 → 监控 → 正式启用。网关不可用时按明确安全规则回退，不能静默绕过必须鉴权/限流的写操作。
- 若后续部署成“保护全部用户 API”的强制入口，必须同时在源站限制旧接口直连或对旧接口施加同等服务端保护，否则网关限流可被直接绕过。

**验收信号：**用户可一键启用/禁用可选路由；未启用时全部旧 API 正常；容器无公网端口/额外管理凭据；故障回滚不影响已成立订单。映射 **GW-107/109/508**。

## 9. 安全否决清单（No-Go）

出现以下任一情况则不启用对应功能：

- 要求在主题 JS、前端主题 manifest 或公开配置中保存长期对称密钥、管理员 token、邮件凭据。
- 为快速下单绕过邮箱验证、强制邀请码、Laravel 账户权限或支付状态机。
- 验证码可以重复成功消费；高风险写操作在 Redis 故障下默认“放行”。
- 网关仅限流新前端，旧接口却允许任何人绕过同等强制安全策略。
- 加密协议没有 Threat Model、算法/密钥轮换评审、抗重放测试、降级策略或 TLS。
- 通用可控代理路由、支付回调/管理员/节点接口被意外纳入网关。
- 将密码、auth_data、Authorization、支付密钥、个人订单或验证码答案输出日志或邮件。
